课程目标

Mindset

不要把 Vibe Coding 讲成“魔法”，要讲成“工程协作”

教学重点不是让 AI 一次生成完美代码，而是让学员知道何时让 AI 探索、何时收敛、何时验证，以及如何把隐性经验沉淀为可复用资产。

1. 从提示词转向任务协议

提示词不是一句“帮我写一个页面”，而是包含目标、约束、上下文、验收标准和风险边界的任务协议。

目标 范围 约束 验收

2. 从代码生成转向上下文工程

AI 的输出质量取决于它能看见什么。学员要学会选择文件、引用文档、拉取 issue、读取数据库结构，并让模型先解释再修改。

代码图谱 业务事实 运行证据

3. 从个人技巧转向团队资产

常用审查清单、代码风格、发布流程、排障路径都应该被写成 Skills 或规则，让团队持续复用同一套经验。

Workflow

推荐课堂主线：六步闭环

每个案例都按同一条主线推进，帮助学员形成稳定肌肉记忆。讲课时先展示完整闭环，再让学员分组复现。

表达意图

把“我要做什么”写清楚：业务目标、用户路径、不可接受的结果、交付物格式。

装配上下文

让 AI 读取相关代码、设计稿、接口文档、日志、issue、数据库 schema，而不是凭空猜。

生成计划

要求 AI 先给改动范围、风险点、验证方式。讲师要强调：计划是用来审查的，不是自动接受的。

小步修改

围绕一个可验证目标推进，避免一次性生成大块无法审查的代码。

运行验证

用测试、lint、类型检查、浏览器自动化、接口请求和日志证据证明结果。

复盘沉淀

把成功模式写入 Skill，把反复出现的坑写入团队规则，把外部事实源接入 MCP。

Skills

Skills 不是“更长的提示词”，而是团队经验的可执行封装

课堂中要让学员亲手写一个 Skill，并在真实任务里调用它。下面这些 Skill 模板可以直接作为训练素材。

需求澄清 Skill

用于把模糊需求转成可实现任务，尤其适合产品故事、客服反馈和口头描述。

技能目标：把输入需求拆成用户目标、边界条件、数据依赖、验收标准和待确认问题。 执行步骤： 1. 先复述业务目标，不写代码。 2. 标出缺失信息，并按“必须确认 / 可以假设 / 后续验证”分类。 3. 输出最小可交付范围和不做范围。 4. 生成可直接放入 issue 的任务说明。

代码库导览 Skill

用于新同学或跨项目修改，让 AI 先读系统结构，再给出修改入口。

技能目标：在修改前建立代码地图。 执行步骤： 1. 搜索路由、入口、测试、配置和领域模型。 2. 画出请求链路或组件树。 3. 标注“高置信入口”和“需要运行确认的入口”。 4. 在给计划前引用具体文件路径。

安全改动 Skill

用于登录、权限、支付、数据导出等高风险区域，要求 AI 先做威胁建模。

技能目标：任何涉及身份、权限、资金、隐私数据的改动都必须先做风险审查。 检查清单： - 输入是否可信，是否需要校验和编码。 - 当前用户是否有权限访问目标资源。 - 日志中是否可能泄漏敏感信息。 - 测试是否覆盖拒绝访问、越权和异常路径。

测试补全 Skill

用于遗留代码或快速迭代后补齐保护网，强调覆盖行为而不是覆盖实现细节。

技能目标：为本次改动补齐最小但有效的测试。 执行步骤： 1. 识别用户可观察行为和失败模式。 2. 优先补单元测试，其次补集成测试或端到端测试。 3. 每个测试名称写清业务含义。 4. 运行测试并解释失败原因，不盲目改断言。
MCP

MCP 的教学重点：让 AI 接触“真实事实源”

MCP 不是插件列表，而是把 AI 从代码仓库扩展到真实工作环境。好的演示要让学员看到：AI 读取事实、引用证据、基于证据修改。

事实源 可接入的 MCP 课堂演示方式 常见风险
需求与缺陷 GitHub Issues、Linear、Jira 让 AI 读取 issue 描述、评论、验收标准，再生成实现计划和测试清单。 评论中可能有过期信息，需要让 AI 标出冲突和时间线。
设计与产品素材 Figma、Notion、Confluence 读取组件尺寸、颜色 token、交互说明，映射到项目已有设计系统。 不要让 AI 绕开现有组件库重写 UI。
运行数据 Postgres、MySQL、BigQuery、Snowflake 查询 schema、样例数据和异常分布，再决定接口字段、迁移和边界测试。 只读账号、脱敏数据、查询限制必须提前配置。
线上故障证据 Sentry、Datadog、Grafana、CloudWatch 读取错误堆栈、日志片段和指标变化，让 AI 反推最可能的代码入口。 日志片段不是完整真相，需要结合代码和复现步骤。
浏览器行为 Playwright、Browser、Chrome DevTools 让 AI 打开页面、复现交互、截图、检查 console 和网络请求。 演示环境要稳定，账号和测试数据要可重置。
Scenarios

六个可直接上课的真实场景

每个场景都包含业务目标、Skills、MCP、课堂操作和示例提示词。讲师可以任选其中一个完整演示，再让学员分组完成另一个。

场景一：从 Figma 到可访问的设置页

任务不是“生成一个设置页面”，而是基于设计稿、组件库和可访问性要求，把已有产品中的设置页补齐并验证交互。

代码库导览 Skill UI 一致性 Skill 测试补全 Skill Figma MCP Playwright MCP
  1. 读取 Figma frame，提取布局、状态、token 和交互说明。
  2. 让 AI 搜索项目已有表单组件、开关组件、设置页路由和测试样例。
  3. 要求 AI 给出“复用组件清单”，禁止直接硬编码样式。
  4. 小步实现页面、空状态、保存成功和错误提示。
  5. 用 Playwright 打开页面，检查键盘导航、表单校验、console 和截图差异。
请先读取 Figma 中“Account Settings / Notification”这个 frame，并结合当前代码库已有设计系统完成分析。 要求： 1. 不要直接写代码，先列出应复用的组件、路由入口、状态管理位置和测试入口。 2. 标出 Figma 和现有组件库不一致的地方。 3. 给出实现计划，必须包含可访问性验证和 Playwright 验证步骤。 4. 等我确认计划后，再分步骤修改。

讲师强调

  • AI 要先读设计和代码，再生成实现。
  • Skills 用来约束“必须复用组件库”。
  • MCP 的价值是让设计稿成为事实源，而不是截图灵感。

交付物

  • 页面实现
  • 组件复用说明
  • 可访问性与浏览器验证记录

场景二：退款策略变更，从 issue 到后端实现

业务提出“部分订单支持自动退款”，学员要让 AI 读取 issue、数据库结构、支付接口和现有测试，完成可审查的后端改动。

需求澄清 Skill 安全改动 Skill 测试补全 Skill GitHub MCP Postgres MCP Stripe 文档 MCP
  1. 读取 GitHub issue 和评论，整理退款策略、边界和未决问题。
  2. 查询订单、支付、退款表结构，确认当前状态机和幂等字段。
  3. 让 AI 先画出退款请求链路，标注权限、金额校验和外部 API 调用点。
  4. 实现策略判断、审计日志和幂等保护。
  5. 补充成功、金额越界、重复请求、无权限和支付服务失败测试。
请使用需求澄清 Skill 和安全改动 Skill 分析 GitHub issue #1284：自动退款策略调整。 请同时读取数据库中的 orders、payments、refunds schema，并回答： 1. 当前状态机如何流转，哪里适合加入新策略。 2. 哪些字段可用于幂等和审计，哪些字段缺失。 3. 哪些边界必须测试：金额、权限、重复请求、外部支付失败。 4. 给出最小改动计划，不要先写代码。

讲师强调

  • 后端场景必须让 AI 接触真实 schema。
  • 支付、权限、资金类改动必须触发安全 Skill。
  • AI 的计划要包含失败路径，不只覆盖 happy path。

可扩展讨论

  • 数据库迁移是否必要
  • 审计日志字段如何设计
  • 如何 mock 外部支付服务

场景三：线上 500 告警排障与修复

让学员体验 AI 不只是写代码，还能连接监控、日志和错误堆栈，形成“证据驱动”的排障路径。

事故排查 Skill 回归测试 Skill Sentry MCP Datadog MCP GitHub MCP
  1. 读取最近的 Sentry issue，提取堆栈、请求参数、用户影响和首次出现版本。
  2. 查询 Datadog 指标，确认是否与部署、流量或第三方服务波动相关。
  3. 让 AI 从堆栈回到代码入口，解释可能原因并提出复现方法。
  4. 先写失败测试或最小复现，再修复空值、竞态或边界处理。
  5. 生成 PR 说明：根因、修复、验证、剩余风险。
请使用事故排查 Skill 分析 Sentry issue “CheckoutSessionError spikes after release 2026.06.17”。 请完成： 1. 汇总堆栈、受影响接口、最近部署和错误趋势。 2. 回到代码库找出最可能入口，并说明依据。 3. 给出一个最小复现或失败测试。 4. 修复前先列出两个可能误判的原因，避免只根据第一条日志下结论。

讲师强调

  • MCP 让 AI 能引用线上证据。
  • 排障要先复现，不能直接“猜修”。
  • PR 描述要服务后续 review 和 incident review。

课堂提问

  • 日志与代码冲突时相信谁？
  • 什么时候应该回滚而不是热修？

场景四：数据看板新增“留存分层”指标

这是一个跨数据、后端和前端的综合场景。关键是让 AI 先确认指标定义和数据口径，再写查询和 UI。

指标定义 Skill 代码库导览 Skill BigQuery MCP Notion MCP GitHub MCP
  1. 读取 Notion 中指标口径：活跃用户、首访日期、留存窗口、排除规则。
  2. 查询数据仓库 schema 和样例行，确认字段可用性。
  3. 让 AI 生成 SQL 草案，但要求解释 join、过滤和性能风险。
  4. 找到现有看板 API 和图表组件，接入新指标。
  5. 添加 SQL 快照测试、API 测试和前端空数据状态。
请使用指标定义 Skill，读取 Notion 页面“Retention Segments v2”和 BigQuery 中 analytics.events、analytics.users 的 schema。 在写代码前请输出： 1. 指标口径，用业务语言和 SQL 语言各描述一次。 2. 需要排除的数据：测试账号、内部账号、缺失首访日期、重复事件。 3. 查询性能风险和建议索引或分区条件。 4. 需要修改的 API、类型定义、图表组件和测试文件。

讲师强调

  • 数据场景最怕“口径猜测”。
  • AI 生成 SQL 后必须解释数据过滤逻辑。
  • 前端展示要考虑空数据、慢查询和权限。

交付物

  • 指标口径说明
  • 查询与 API 实现
  • 看板 UI 与测试

场景五：遗留表单重构，保持行为不变

让学员学习“AI 辅助重构”的正确姿势：先锁定现有行为，再小步替换，而不是让 AI 一次重写整个模块。

行为保护 Skill 测试补全 Skill Playwright MCP GitHub MCP
  1. 让 AI 阅读遗留表单和近期 bug PR，整理现有行为清单。
  2. 用 Playwright 录制当前交互：必填校验、动态字段、提交失败、成功跳转。
  3. 补充保护性测试，确保重构前测试能描述行为。
  4. 分离数据转换、校验、UI 组件，逐步替换。
  5. 对比重构前后截图和网络请求，确认行为不变。
请使用行为保护 Skill 分析 LegacyProfileForm。 要求： 1. 先列出现有用户行为，不评价代码质量。 2. 找到最近 3 个与该表单相关的 bugfix PR，提取不能破坏的边界。 3. 设计重构前必须补的测试。 4. 重构计划必须按小步提交组织，每一步都有验证方式。

讲师强调

  • 重构不是重新生成。
  • Skills 用来强制“先保护行为”。
  • 浏览器 MCP 可作为可视化回归证据。

常见错误

  • 让 AI 删除看似无用的分支
  • 只看单元测试，不看真实交互
  • 忽略历史 bug 的业务原因

场景六：客服反馈批量归因，生成修复候选

这个场景适合展示 AI 如何把非结构化反馈转成工程任务：读取 Slack、工单、日志和代码，找出高价值修复点。

反馈归因 Skill 需求澄清 Skill Slack MCP Zendesk MCP Datadog MCP GitHub MCP
  1. 读取一组客服工单和 Slack 讨论，按用户意图和失败现象聚类。
  2. 抽取复现步骤、账号类型、设备、时间和错误提示。
  3. 结合日志或指标确认是否存在系统性问题。
  4. 让 AI 输出修复候选：文案问题、交互问题、后端错误、配置问题。
  5. 将最高价值候选转成 issue，包含证据、范围、验收标准和测试建议。
请使用反馈归因 Skill，读取最近一周带有 “cannot export invoice” 标签的 Zendesk 工单和相关 Slack 线程。 请输出： 1. 反馈聚类，每类包含代表工单、用户影响和置信度。 2. 需要进一步验证的日志或指标。 3. 最可能的代码入口或配置入口。 4. 一个可交给工程团队的 issue 草案，包含验收标准和测试建议。

讲师强调

  • AI 适合做信息归纳，但必须保留证据链接。
  • 不要把所有反馈都转成代码改动。
  • 好的输出应该能直接进入工程队列。

延伸练习

  • 让学员比较 AI 聚类和人工聚类
  • 讨论隐私数据脱敏策略
Labs

课堂练习设计：让学员真的跑一遍闭环

练习不要只让学员“写提示词”。每个小组都应该产出计划、代码、验证证据和复盘 Skill。

STEP 01

任务拆解

小组选择一个场景，把业务目标转成任务协议：目标、上下文、约束、验收。

STEP 02

上下文装配

至少引入两个事实源：代码库加一个 MCP，例如 issue、Figma、数据库或日志。

STEP 03

实现验证

按 AI 计划小步修改，并留下测试、截图、日志或命令输出作为证据。

STEP 04

沉淀复盘

每组把一个可复用经验写成 Skill，并说明下次何时触发。

讲师观察清单

  • 学员是否要求 AI 先读上下文，而不是直接写代码。
  • 计划中是否有风险、文件范围和验证方式。
  • 是否正确使用 Skill 约束输出，而不是每次重新解释团队规范。
  • MCP 输出是否被引用为证据，还是只被当作背景材料。
  • 最终提交是否包含测试或可复现验证记录。
Rubric

评价标准：看交付能力，不看提示词花哨程度

用下面的标准给课堂成果打分，可以避免学员把重点放在“模型说得好听”，而忽略工程质量。

维度 优秀表现 需要提醒
任务表达 目标、约束、验收、不做范围清楚，AI 能复述任务并发现缺口。 只有一句“帮我实现”，缺少业务边界和风险说明。
上下文质量 同时读取代码、文档、issue、数据或运行证据，并引用具体来源。 只依赖聊天上下文或模型常识。
Skills 使用 能把团队规范、审查清单和重复流程封装为 Skill，并在任务中触发。 每次手写长提示词，或 Skill 与实际任务无关。
MCP 使用 让 AI 读取真实事实源，并据此改变计划或实现。 只展示“能连上”，没有用于决策。
验证闭环 有测试、截图、日志、命令输出或查询结果作为证据。 仅凭 AI 自述“已经完成”。
交付表达 PR 或汇报包含改动摘要、验证、风险和后续建议。 只粘贴代码，没有说明为什么这样改。

讲课开场白建议

“今天我们不学习如何让 AI 替你写代码，而是学习如何像技术负责人一样指挥一个会写代码、会读资料、会跑验证的协作者。 你给它的不是一句提示词，而是一套工程上下文和验收协议。”

课堂避坑提醒

  • 不要用玩具需求做主案例，学员会误以为 Vibe Coding 只适合 demo。
  • 不要只展示成功生成代码，要展示 AI 读错、跑失败、再修正的过程。
  • 不要把 MCP 讲成工具清单，要讲清它如何改变 AI 的判断依据。
  • 不要把 Skills 当提示词收藏夹，要让它承载团队规范和流程。

这些问答适合放在课程结尾，用来把学员的兴奋感拉回到可落地的工作方式。

Vibe Coding 是否意味着不需要懂代码？
不是。它降低了从想法到代码的摩擦，但提高了对任务拆解、系统理解、验证和审查的要求。懂工程的人会更容易把 AI 变成生产力。
什么时候不应该让 AI 直接改代码？
当需求不清、上下文不足、涉及权限资金隐私、缺少验证环境、或改动跨多个系统时，应先让 AI 做分析、风险识别和计划。
Skills 和项目规则有什么区别？
项目规则更像长期约束，例如代码风格和团队约定；Skills 更像可触发的任务流程，例如“做事故排查”“补测试”“做安全改动”。
MCP 最适合优先接哪些系统？
优先接“经常影响代码决策”的事实源：issue、设计稿、数据库 schema、日志监控、浏览器自动化和团队文档。不要为了数量而接入。
