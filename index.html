Teaching framework

教学主线：让 AI 从“代码补全器”变成“工程协作者”。

每个案例都按同一条闭环推进：先澄清目标和边界，再补充上下文，随后让 AI 计划、小步修改、运行验证，最后沉淀为团队资产。

任务协议模式

先让学员学会“怎么把工作讲清楚”。

  • 把模糊需求拆成业务目标、用户路径、约束和验收标准。
  • 要求 AI 先复述理解、列出缺失信息，再给实现计划。
  • 课堂重点：不是提示词越长越好，而是上下文越准确越好。

Skill 沉淀模式

把团队规范和重复流程变成可调用能力。

  • 把“安全改动”“测试补全”“代码库导览”等流程写成 Skill。
  • 让 AI 按固定检查清单执行，减少每次重新解释规范的成本。
  • 课堂重点：Skill 不是提示词收藏夹，而是团队 SOP 的执行入口。

MCP 事实连接模式

让 AI 能读到真实世界，而不是只凭模型常识猜。

  • 接入 GitHub、Figma、数据库、Sentry、Datadog、Playwright 等事实源。
  • 要求 AI 引用证据，并说明这些证据如何改变实现方案。
  • 课堂重点：MCP 的价值不是“连上了”，而是“影响了决策”。

Skills in practice

把经验写成 Skills，让每次 Vibe Coding 都站在团队肩膀上。

讲课时不要只介绍 Skill 概念，要让学员亲手写一个、调用一次、验证一次。下面这些 Skill 可以作为课堂模板。

01

需求澄清 Skill

把口头需求转成目标、边界、依赖、验收和待确认问题，适合产品故事和客服反馈。

02

安全改动 Skill

登录、权限、支付、隐私数据相关改动必须先检查输入、权限、审计、日志和失败路径。

03

代码库导览 Skill

修改前先让 AI 搜索入口、路由、领域模型、测试和配置，画出请求链路或组件树。

04

测试补全 Skill

优先覆盖用户可观察行为和失败模式，避免只为了覆盖率而测试实现细节。

MCP as real context

MCP 要放进具体场景里讲，而不是做工具清单展示。

好的 MCP 教学会让学员看到 AI 如何读取事实、引用证据、修正计划，并把这些证据写进验证记录。

Real scenarios

六个真实场景，把 Skills 和 MCP 放进同一条工作流。

这些场景可以直接拿来做内训。建议讲师先完整演示一个，再让学员分组完成另一个，并要求提交验证证据。

01

从 Figma 到可访问的设置页

读取设计稿、复用组件库、实现保存状态，并用 Playwright 验证键盘导航和表单错误。

UI 一致性 SkillFigma MCPPlaywright MCP
请先读取 Figma frame 和当前组件库，列出复用组件、路由入口、状态管理和可访问性验证计划，不要先写代码。
02

退款策略变更与幂等保护

从 issue、数据库 schema 和支付文档出发，设计退款状态机、权限校验、审计日志和失败测试。

安全改动 SkillGitHub MCPPostgres MCP
读取退款需求 issue、orders/payments/refunds schema，先输出状态机、幂等字段、风险点和测试清单。
03

线上 500 告警排障

让 AI 读取 Sentry 堆栈、Datadog 指标和最近部署，先复现问题，再修复并补回归测试。

事故排查 SkillSentry MCPDatadog MCP
汇总错误趋势、受影响接口和最近部署；回到代码找入口；先写最小复现或失败测试，再提出修复方案。
04

留存分层指标进入数据看板

读取 Notion 指标口径和 BigQuery schema，生成 SQL、API、图表和空数据状态的完整改动计划。

指标定义 SkillNotion MCPBigQuery MCP
先用业务语言和 SQL 语言分别描述指标口径，再列出数据排除规则、性能风险、API 和测试入口。
05

遗留表单重构但行为不变

读取历史 bugfix PR，录制当前交互，补保护性测试，再小步拆分校验、转换和 UI 组件。

行为保护 SkillGitHub MCPBrowser MCP
先列出现有用户行为和不能破坏的历史 bug 边界，再设计重构前必须补的测试和每一步验证方式。
06

客服反馈批量归因

从 Zendesk、Slack 和日志中聚类反馈，区分文案、交互、配置和代码问题，生成高质量工程 issue。

反馈归因 SkillSlack MCPZendesk MCP
读取一周工单和相关讨论，按失败现象聚类，保留证据链接，输出可交给工程团队的 issue 草案。

Classroom flow

一节课就围绕一条闭环反复练。

1

定目标

写清业务目标、用户影响、交付物和不做范围。

2

装上下文

让 AI 读取代码、文档、issue、设计稿、日志或数据库。

3

调 Skill

根据任务类型调用需求澄清、安全、测试、排障等 Skill。

4

接 MCP

要求 AI 引用外部事实源，并说明证据如何影响计划。

5

小步改

按可验证目标推进，避免一次性生成无法审查的大块代码。

6

跑验证

留下测试、截图、日志、查询结果或命令输出作为证据。

Hands-on lab

课堂练习：每组交付一个可审查的 AI 协作结果。

不要只让学员提交提示词。每组必须提交任务协议、上下文来源、调用的 Skill、MCP 证据、代码改动、验证记录和复盘沉淀。
